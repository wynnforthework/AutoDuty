# 步骤执行机制统一审查：0.0.0.398

审查日期：2026-11-19。范围：步骤开始、执行队列、成功判定、交接、超时、重试；不更改副本路线文件。

## 结论

问题不是所有动作都没有状态检查，而是主执行器、独立任务队列和计时器没有统一遵守这些检查。仅增加固定等待无法消除这类不一致。本轮已修复通用执行链，不宣称所有副本特殊动作都具备业务结果验证。

## 发现与处理

| 位置 | 发现 | 本轮处理 |
| --- | --- | --- |
| Framework_Update / TaskManager | 主执行器因未就绪返回，任务队列仍有独立的更新回调 | TaskManager 使用 StepMode，由 AutoDuty 在主更新之后驱动；暂停、加载、过场、已认领传送或待处理失败时不执行路线任务 |
| UpdateStepAttempt | 稳定就绪检查偏重寻路，动作阶段保护不完整 | 统一世界就绪检查；每步开始需前置状态持续就绪 1 秒。条件再次失效就重置观察窗口，不能靠时间流逝放行 |
| 对话 / 等待动作 | 全部强制完全空闲、网格就绪会阻塞选择窗口及状态观察 | SelectString、SelectYesno、SelectJournalResult、WaitFor、ClickTalk 保留占用状态下的入口；无坐标动作、TeleportTo、明确的 MoveTo false 不依赖网格就绪 |
| TryAdvanceAtDestination / StageAction | 到达或队列变空后可立即交接，容易错过延迟加载 | 到达后停止旧寻路并观察 1 秒；队列变空后也需状态持续就绪 1 秒，仍检查 ConditionsUntil；新步骤不能复用旧步骤的完成观察 |
| StepAttempt 时钟 | 移动、动作、任务队列、重试等待采用不同的暂停处理 | 共用 Suspend 计算暂停增量；暂停、加载及就绪等待冻结相应时钟；同一时刻重复调用不会重复补时 |
| 重试网格检查 | 较早的就绪返回让 StageReadingPath 内的网格超时检查不可达 | 在就绪等待分支检查网格重试期限；加载不耗该期限，单纯等待网格不能不断延长自身期限 |
| 动作超时分类 | KillInRange 使用一般动作期限，AutoMoveFor 可能早于指定时长超时 | 范围战斗使用战斗期限；AutoMoveFor 与 Wait 根据指定时长加宽限计算；WaitFor 原有禁用超时设置保留 |
| Interactable | 找到对象后对象丢失，有一条分支直接 Abort，空队列被当成成功 | 改为报告 interaction-object-missing，由统一失败处理决定重试，不当作完成 |
| KillInRange | 单次空对象列表即可完成 | 要求连续观察空范围，且不在队伍战斗中；瞬间为空不立即推进 |
| Wait / AutoMoveFor | 共享 EzThrottler 计时器；暂停或加载仍消耗等待时间 | 每次调用独立计时，依据可暂停的动作时间计算 |
| 参数校验 | 非法范围、负时长、没有合法对象编号可能静默返回 | 在执行前报告 invalid-arguments，防止无操作被当作成功 |
| 397 区域恢复 | 取消旧工作时可能清掉已经报告的失败 | 保留失败信号，有失败不能按普通加载恢复自动重发 |
| 导航诊断 | 只能看到阶段和动作，不易知道为什么等待 | 增加 executionStatus，包含当前等待状态 |

## 执行规则

1. 新步骤先检查角色、占用状态与该步骤实际需要的依赖；前置状态连续稳定后才开始。
2. 任务队列每帧执行前再次确认路线没有暂停、加载、传送或待处理失败。
3. 完成依据仍是该动作的实际判断：移动到达、窗口操作结果、交互变化、战斗结果或显式等待条件。增加的稳定观察期本身不能让动作成功。
4. 角色暂时不能执行时保留步骤及任务，不消耗对应执行超时；就绪后重新观察，再继续。
5. 失败才进入重试；初次执行不是重试。失败的寻路不得通过跳步补偿。
6. 397 中的延迟加载恢复继续适用：未被当前动作认领的加载，稳定后只重发可安全恢复的当前 MoveTo；死亡和返回入口仍走独立恢复，不把传送当作步骤完成。

## 验证

已运行 tests/AutoDuty.Tests 的完整测试程序。新增覆盖：

- 两分钟加载不会因墙钟经过自动放行；重复加载重置稳定窗口。
- 暂停、加载、传送、失败状态的任务执行组合；正常入队/副本外循环不被路线限制误挡。
- 新步骤不复用旧步骤的就绪及完成证据。
- 不需要网格的动作不被网格状态阻塞。
- 移动、动作、任务期限同时冻结，重复暂停不重算，失败次数和步骤序号不改变。
- 加载冻结重试等待，而单纯网格等待仍有上限。
- 战斗与显式时长动作的超时分类、长整数溢出边界。
- 独立 Wait 计时、暂停期间不消耗等待时长、非法动作参数拒绝及旧格式对象编号兼容。

Release 编译和完整测试通过。仍有仓库原有编译及依赖告警。测试是离线状态与模型回归，没有在游戏里复现所有窗口、战斗、过场和传送；需要以下实测。

## 游戏内验收

- 优先重跑万相森国第 7～9 步、巴别塔第 20～24 步，确认加载时不再误报、没有跳步，坐标变化后重新寻路。
- 慢加载或网格重建时观察“等待”提示，加载恢复后继续；真正的网格失败仍应到期限暂停。
- 使用包含对话、选择选项、交互传送的路线，检查窗口未就绪时不乱点、对话占用不会阻止下一步选择。
- Wait 中暂停超过等待时长，再恢复，确认执行剩余等待；动作完成后等待观察期，加载信号到达则停止旧工作。
- 检查正常 Boss 战、范围杀怪、战斗中断移动、Boss 完成后退出副本。
- 检查 Stop、暂停/恢复、死亡返回入口、连续自动练级及再次进入同一副本，避免队列生命周期回归。

## 边界与后续

稳定观察期为 1 秒，是检查状态的最低持续时间，不是“等满就执行”的定时跳步。它不能预测尚未到达客户端的事件；特别晚的加载仍由 397 的恢复处理。未增加全局每步盲等 2 秒的设置。

Wait、AutoMoveFor 本来就是显式时长动作，完成含义仍是指定时间结束或其原有中断条件，不等同于“已到达某地图”。AutoMoveFor 不适合作为任何未知传送成功的通用证明。

Jump、JumpTo 以及 DutySpecificCode 中仍有按时间安排的特殊操作，本轮保留其脚本语义，但纳入公共队列的加载/暂停保护；它们没有因此获得完整的业务结果验证。后续应按具体动作建立落地、对象变化或地图变化等结果契约。

Interactable 的对象消失、对话结束等成功条件仍沿用现有实现；“对象消失必然代表交互成功”不能对所有副本成立。缺少通用游戏证据的特殊交互应配置 ConditionsUntil 或提供明确的任务/物品/地图结果判定，不能靠无限增加等待解决。
