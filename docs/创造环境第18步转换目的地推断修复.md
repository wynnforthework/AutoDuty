# 创造环境第 18 步转换目的地推断修复（0.0.0.399.4）

2026-11-20 用户实测：0.0.0.399.3 在创造环境极北造物院（974）第 18 步报 movement-transfer-timeout / destination-unknown。第 17、18 步仍为旧平台 Y≈500，第 19 步 WaitFor IsReady、第 20 步零坐标 StopForCombat false，第 21 步才是新平台 Y≈624 的 MoveTo。

本地此前增加的目的区域验证只有两步前瞻：遇到 WaitFor IsReady 就取紧邻的后一步坐标。第 20 步没有空间坐标，因此虽然转换已被观察到，目的区域仍为 null，最终超时暂停。不是本次日志证明 vnavmesh 寻路失败，也不能用固定加等待时间修复。此前测试没有覆盖“就绪检查与新平台坐标之间存在零坐标控制动作”的真实脚本结构。

## 修正

- 从触发步骤向后最多检查 8 条；只越过无条件、零坐标的 WaitFor IsReady、StopForCombat false 和注释，查找第一条允许的空间动作。保留既有 WaitFor IsReady 所建立的转换意图约束，不能仅凭任意远处坐标认定转换。
- 遇到跳步、传送、交互、开启战斗、其它条件等待或带条件的中间动作，停止推断，不穿过这些边界猜目的地。显式 Transition 配置继续优先。
- 加载转换和无加载强制移动共用这套路线前瞻，避免两个入口得到不同目的地；目的区域仍验证高度、水平范围、地面和持续就绪等证据，只有原第 18 步可消费这份完成证据。
- 推断只读取后续信息，不更改索引顺序或删步骤；完成第 18 步后仍执行第 19、20 步，不会直接跳到 21。无需修改或重新下载原始脚本。
- 增加 transfer-destination 诊断事件，记录显式/路线推断/未知来源、目的区域及后续空间坐标。

## 验证和边界

新增测试直接读取仓库 `(974) Ktisis Hyperboreia.json`，先复现旧两步推断得到 null，再验证第 18 步能解析到第 21 步目的平台。覆盖慢加载、旧楼层不完成、缺少地面不完成、落地稳定确认、证据仅归属第 18 步、危险动作边界和前瞻上限。既有弹射平台与其它转换回归同时运行。

Release 编译零错误，35 组离线测试通过；尚未游戏实测。目的区域沿用原推断的 100m 水平范围和 3m 高度容差，不保证所有平台形状或同高相邻区域均可自动区分；无法可靠推断时仍需显式 Transition 配置。未新增 Dalamud API / IPC，复用现有路线模型和转换验证接口。
