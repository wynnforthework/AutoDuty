# AutoDuty 副本挂机：可靠性 / 可调试性 / 录制 改造计划

> 仓库：`d:\UGit\AutoDuty`（Dalamud 插件，net10.0-windows，Dalamud API 15）
> 分支：`dev_01`（remote `origin` = wynnforthework/AutoDuty，`upstream` = erdelf/AutoDuty）
> 编写日期：2026-11-16

---

## 1. Context（为什么改）

AutoDuty 的副本挂机是"读一个 JSON 脚本 → 一个动作一个动作执行"。脚本在 `%config%/AutoDuty/paths/(territoryId) Name.json`，仓库内另有 315 份同格式路径随 Patcher 增量下发。

实际使用中反复出现三类问题，而当前实现**没有任何"步骤失败"的概念**：

1. **脚本漏了动作**（比如少一个交互步骤）——下一步因为缺前置条件而无法完成，然后被静默跳过。
2. **寻路卡墙**——`vnavmesh` 沿墙摩擦，`StuckHelper` 会无限重试或直接 `/return`，但对"这一步永远做不完"没有判断。
3. **出错即连锁跳过**——动作超时是**静默**的（`TaskManager` 默认 `TimeoutSilently = true`），`indexer++` 一路推进，最后整个副本的编排全错。

同时，挂机期间构建 Tab 被整体禁用（`BuildTab.cs:60`），既不能改脚本也不能回到某一步，错误只能一次次重演。

### 已确认的决策
| 项 | 决定 |
|---|---|
| 改造方式 | **直接改 AutoDuty**，不新建插件 |
| 失败策略 | 每步独立重试（默认 3 次）→ 超过则**暂停挂机 + 高亮失败步 + 声音/聊天提示**，不静默跳过 |
| v1 范围 | 失败检测与重试、跳步/回退/热改、录制建路径、按职能分流 + 练级排除 |
| 网格重建 | **每次插件启动后，首次进入某副本时 rebuild 一次**（会话级记忆，可关闭） |

## 3. 设计总览

三个新增模块 + 沿现有结构的最小侵入改造：

```
                    ┌──────────────────────────────┐
   Plugin.Actions   │  StepAttemptTracker          │  每步：尝试次数 / 是否真的开始移动 / 失败原因
   Plugin.indexer ──┤  StepFailure                 │  失败快照：步号 + 原因 + 时间
                    └──────────┬───────────────────┘
                               │
      ┌────────────────────────┼─────────────────────────┐
      ▼                        ▼                         ▼
  FailCurrentStep()      SeekToStep(index)         PathRecorder
  重试 → 超限暂停         跳步/回退/热改后重定位       录制建路径
      │                        │
      ▼                        ▼
  红色横幅 + 声音 + 聊天    主列表点击 / 右键菜单 / Overlay
```

**核心原则：不引入新的静默失败。** 每一个"放弃这一步"都必须有一条可见记录（日志 Warning 起步 + UI 高亮）。

## 4. 阶段 0：基础设施（半天）

### 4.1 失败状态的数据结构

新增 `AutoDuty/Helpers/StepAttemptTracker.cs`：

```csharp
internal sealed class StepAttempt
{
    public int     Index           { get; init; } = -1;
    public PathAction? Action      { get; init; }
    public int     Attempts;                     // 已失败次数
    public long    StartedAt;                    // Environment.TickCount64
    public bool    MovementStarted;              // 见到过 waypoint / IsRunning / PathfindInProgress
    public Vector3 StartPosition;                // 首次进入本步时的玩家位置
    public long    LastProgressAt;               // 上次"有进展"的时间
    public string? LastFailReason;
}

internal sealed class StepFailure
{
    public int    Index;
    public string Reason;        // 稳定 key，便于本地化与统计
    public string Detail;        // 人读的补充（错误码/坐标/异常）
    public int    Attempts;
}
```

`AutoDuty.cs` 增加：
```csharp
internal StepAttempt?  currentAttempt;
internal StepFailure?  currentFailure;
internal readonly Dictionary<int, StepAttempt> attemptHistory = [];  // 便于日志/统计
```

**生命周期**：在 `Framework_Update` 开头（`AutoDuty.cs:2064` 之前）检测 `indexer != currentAttempt?.Index` → `BeginAttempt(indexer)`。这样**不必改动十余处裸 `indexer++`**（`:438, 1008, 1383, 1390, 1397, 1404, 1411, 1418, 1425, 1537, 1564, 2081`），风险最低。

### 4.2 三个统一入口

在 `AutoDuty.cs` 加：


### 4.3 重试 / 暂停策略

```
RegisterStepFailure(reason):
    currentAttempt.Attempts++
    currentAttempt.LastFailReason = reason
    日志 Warning：步号、动作 ToCustomString()、原因、第 n/Max 次
    if attempts < MaxStepRetries:
        taskManager.Abort(); VNavmesh.Path_Stop(); /automove off
        StuckHelper.ResetForStep()          // 关键：同一步重试要清零卡住计数
        Stage = Stage.Reading_Path          // 原地重新寻路
    else:
        FailCurrentStep(reason)             // → 暂停
```

`FailCurrentStep`：
```
currentFailure = new StepFailure{...}
Stage = Stage.Paused                       // 复用现有暂停：停寻路 + StepMode=true + 统计结算
States |= PluginState.Failed               // 新增 flag = 1 << 4
聊天：/echo  [AutoDuty] 第 N 步失败：<原因>（已重试 M 次），已暂停
声音：Svc.Sound.Play(default 音效，可配)

```

恢复：`Resume` 时若 `currentFailure != null` → 清 `Stage.Failed`、`currentAttempt.Attempts = 0`、`Stage = Stage.Reading_Path`（**重跑失败步**，而不是还原 `previousStage`）。这是现有 `Stage.Paused` 语义唯一需要改的地方：`MainWindow.StopResumePause`（`MainWindow.cs:88-116`）与 `/ad resume`（`AutoDuty.cs:389-397`）两处，抽成一个 `Plugin.ResumeFromPause()`。

## 5. 阶段 1：失败检测（1~2 天）

按"信号源"逐个堵漏，对应 §2.2 的 A/B/C/D。

### 5.1 寻路失败（A + B）

**`StageReadingPath`（`AutoDuty.cs:1440-1450`）**
```csharp
bool started = pathAction is { Name: "MoveTo", Arguments.Count: > 0 }
               && bool.TryParse(pathAction.Arguments[0], out bool useMesh) && !useMesh
    ? (VNavmesh_IPCSubscriber.Path_MoveTo([...], false), true)          // 直线移动无返回值
    : VNavmesh_IPCSubscriber.SimpleMove_PathfindAndMoveTo(pathAction.Position, false);

if (!started) { RegisterStepFailure("pathfind-rejected", pos.ToString()); return; }
currentAttempt.MovementStarted = true;
Stage = Stage.Moving;
```
`Path_MoveTo` 无返回值，走直线时改为在 `StageMoving` 里用"位移是否变化"兜底。

**`StageMoving` 到达判定（`AutoDuty.cs:1529-1531`）** 改为：
```csharp
bool withinRange = dist <= (Interactable ? 2f : 0.25f);
bool pathDone    = !PathfindInProgress && Path_NumWaypoints == 0;

// 新增：路点观测
if (PathfindInProgress || Path_IsRunning || Path_NumWaypoints > 0)
    currentAttempt.MovementStarted = true;

// 拒绝"寻路尚未开始就已结束"
bool reallyArrived = withinRange
    || (pathDone && currentAttempt.MovementStarted)
    || (pathDone && now - currentAttempt.StartedAt < 2000);   // 2s 宽限，兼容零长度路径
```
宽限期是为了不破坏现有 315 份路径里那些"目标就在脚下"的步骤。

**移动阶段超时**：`now - StartedAt > MoveToStepTimeoutMs` 且 `!MovementStarted` → `RegisterStepFailure("no-path")`；若已开始移动则交给 `StuckHelper` 判定。

### 5.2 卡住（对接现有 StuckHelper）

- `StuckHelper` 增 `ResetForStep()`（把 `counter = 0`、`index` 置为当前步），在 `RegisterStepFailure` 里调用。
- 保留现有 Return/Rebuild 阶梯，但增加**最终上限**：同一步 `stuckCount >= MaxStepRetries * StuckReturnX`（约 30）时不再无限循环，改为 `FailCurrentStep("stuck")`。
- 若 `StuckHelper` 判定卡住但距目标已 < 3y（常见的"贴墙差一点"），先尝试**放宽容差重寻路一次**（`SetTolerance(0.5f)`），再走重试。

### 5.3 动作挂死（C）

在 `StageAction`（`AutoDuty.cs:1549`）加**看门狗**，一处覆盖所有动作（Boss / Interactable / WaitFor / KillInRange / 自定义）：

```csharp
long elapsed = now - currentAttempt.ActionStartedAt;
long limit = pathAction.Name switch {
    "Boss"                                   => BossStepTimeoutMs,
    "WaitFor" when 参数为 IsReady/IsValid/... => config 中的 WaitFor 上限或 int.MaxValue 允许,
    "Wait"                                   => 参数里的毫秒 + 30s,
    _                                        => ActionStepTimeoutMs,
};
if (taskManager.IsBusy && elapsed > limit) { RegisterStepFailure("action-timeout"); return; }
```
**暂停计时**：`WatchingCutscene` / `OccupiedInQuestEvent` / `BetweenAreas` 期间不计时（`Svc.Condition`），避免长演出误判。

`WaitFor` 的"无限等待"是设计意图（`new TaskManagerConfiguration(int.MaxValue)`），需在超时表里显式豁免，但给一个可选的总上限（默认 0 = 不限）。

### 5.4 Boss 刷不出来

`ActionsManager.Boss`（`:778-813`）里把 `Boss-GetBossObject` 与 `Boss-WaitInCombat` 显式化：
- 到达 Boss 点后，`BossSpawnTimeoutMs` 内找不到 `IsBoss` 对象 → 本步失败（原因 `boss-missing`）
- 找到后等待 `InCombat` 用 `BossSpawnTimeoutMs`（而非 10s 静默超时）
- 移除 `Boss-BossCheck` 的 `int.MaxValue` 兜底陷阱：改为"Boss 死亡或脱战"双条件，并挂到看门狗下

这条直接解决"漏了动作 → Boss 没刷 → 静默完成"的连锁。

### 5.5 `Conditions` 的严格模式

`AutoDuty.cs:1422-1427` 保留默认"跳过"，但新增 `PathActionFlags.StrictConditions`（`Data/Enums.cs:346` 加 `1 << 1`）：
- 置位且条件不满足 → `RegisterStepFailure("condition-unmet")`
- BuildTab 动作编辑窗加一个勾选框
- 建路径时可以给"我确信这里必须有"的步骤开启

### 5.6 `ConditionsWhile` 中止

`AutoDuty.cs:2073-2083` 的 `indexer++` 改为：日志升到 **Warning** 并记录到 `attemptHistory`，然后走正常跳过（这是作者显式写的"中断条件"，不算执行失败），但 UI 里用灰黄色标出"因中断条件跳过"，让"哪一步被跳了"可追溯。

### 6.3 热编辑的 indexer 漂移规则

所有对 `Plugin.Actions` 的变更都收敛到一个工具函数（新增 `AutoDuty/Helpers/PathEditHelper.cs`）：

```csharp
internal static void MutateActions(Action<List<PathAction>> mutate, string reason)
{
    PathAction? running = Plugin.indexer.InRange() ? Plugin.Actions[Plugin.indexer] : null;
    mutate(Plugin.Actions);

    if (running != null && Plugin.Actions.Contains(running))
        Plugin.indexer = Plugin.Actions.IndexOf(running);   // 引用身份定位
    else
        Plugin.indexer = Math.Clamp(Plugin.indexer, 0, Plugin.Actions.Count);

    Plugin.BeginAttempt(Plugin.indexer);
}
```

规则明细：
| 操作 | 结果 |
|---|---|
| 在第 i 步**之前**插入 | 当前步引用仍在列表里 → 自动跟随，indexer 顺延 |
| 在第 i 步**之后**插入 | indexer 不变 |
| 删除当前步**之前**的步 | 自动跟随 |
| **删除当前步** | 引用消失 → indexer 停在原位（即下一步）并 `BeginAttempt`（不重跑） |
| **编辑当前步**（`ActionEditWindow` 写回的是 `JSONClone` 新实例） | 必须识别为"替换" → `RegisterStepFailure("edited")` 或直接 `SeekToStep(same)` 重跑该步 |
| 拖拽换序 | 引用不变 → 自动跟随 |
| 循环末尾（indexer == Count） | 保持 Count |

依赖"引用身份"是可行的：`PathAction` 是 `class`（`Classes.cs:107`），拖拽换序只交换引用（`BuildTab.cs:329-335`）。

### 6.4 运行中保存

把 `BuildTab.cs:192-234` 抽成 `BuildTab.SavePath(bool bumpChangelog = true)`，热编辑面板提供 `应用并保存` 按钮。保存只写文件，不影响正在跑的 `Plugin.Actions`（运行时副本），下一次 `LoadPath()` 才生效——语义清晰。

### 6.5 明确不改的东西
`MultiboxUtility` 的 `MultiboxBlockingNextStep` / `stepBlock` / `SendPath()`（`Multibox.cs:463, 595-603`）依赖 indexer 同步。`SeekToStep` 在多开模式下**必须广播**（复用现有 `stepBlock` 通道），否则 Host/Client 漂移。这是本阶段最容易引入回归的点，测试时优先验证。

## 7. 阶段 3：录制式建路径（2~3 天）

新增 `AutoDuty/Helpers/PathRecorder.cs`，由 `Framework_Update` 每帧 tick。

### 7.1 采样
```
Recording && Player.Available && Player.IsReady
  && !PartyInCombat
  && 距上次采样点 >= MinSampleDistance (默认 8y)   → 追加 MoveTo(Player.Position)
  && |ΔY| >= 3y                                    → 强制采样（跳跃/落差）
```
用"玩家实际走过的位置"而不是重放 vnavmesh 路点（IPC 没有 waypoint getter）。停止录制时跑 **Ramer–Douglas–Peucker**（ε = 2.5y）精简，顺带去掉抖动。

### 7.2 事件识别（全部可开关）

| 事件 | 判据 | 插入 |

| Boss | `ObjectHelper.IsBoss(obj)` 且 targetable 且在 50y 内，且最近 20 步内无 Boss | `Boss` @ boss 位置，Note = boss 名 |

## 10. 阶段 6：文件格式治理 + 字符串分享（1~2 天）

### 10.1 现有 JSON 的问题（只列真正的病）

| 问题 | 证据 | 后果 |
|---|---|---|
| 条件多态用 `$type` 存**程序集限定名** | `ConfigurationMain.cs:826-836` 的 `JsonSerializerSettings` 开了 `TypeNameHandling.Auto`；条件序列化成 `"$type": "AutoDuty.Data.PathActionConditionToDo, AutoDuty"`（例：`Paths/(1036) Sastasha.json:179`） | 改命名空间/程序集名就要写兼容 binder（**已经发生过**：`AutoDutySerializationBinder`，`ConfigurationMain.cs:838-863`）；分享出去的字符串里塞满 `AutoDuty.Data...` 噪音；跨版本、跨分支易坏 |
| `Position` 是 `{"X":..,"Y":..,"Z":..}` 对象 | `Data/Classes.cs:113` | 每点约 60 字节；两份 W2W 变体路径动辄 10KB，体积绝大部分在这里 |
| 默认值全部写出（`Tag:None`、`Arguments:[]`、`Conditions:[]`、`Note:""`） | 任意 `AutoDuty/Paths/*.json` | 每动作约 200 字节，实际信息量不到 20 |
| `Arguments` 是 `List<string>`，运行期 `TryParse` | `Classes.cs:115`；如 `AutoDuty.cs:1445` 解析 `MoveTo` 的 mesh 标志 | 参数写错**不报错**，动作静默 no-op——与本次「消灭静默失败」的目标直接冲突 |

### 10.2 结论：不换格式，修格式

不推荐换 YAML / TOML / SQLite：多一个依赖、315 份文件要迁移、PR 里反而更难审（路径是靠 GitHub raw + md5 分发的，必须 git-diff 友好）。JSON 的问题出在**序列化契约**，不在 JSON。

做四件事，原则统一为 **写新格式、读新旧两种**（保证 315 份内置文件与历史分享数据不失效）：

**① 条件多态改成显式判别字段**
```jsonc
// 旧（读）: { "$type": "AutoDuty.Data.PathActionConditionDistance, AutoDuty", "Distance": 5 }
// 新（写）: { "Condition": "Distance", "Distance": 5 }
```
- 新增 `PathActionConditionConverter : JsonConverter<PathActionCondition>`：写出时写 `Condition = ParseKey.ToString()`；读取时先看 `Condition`，没有则回退读 `$type` 并用现有 `PARSE_KEYS` + `AutoDutySerializationBinder` 映射。
- 一次性收益：与程序集/命名空间解绑，这是 8.1 元数据共享和 10.3 字符串分享的**共同前置**。

**② `Position` 改成数组**
```jsonc
"Position": [8, -202.74, -31.23]
```
- `Vector3Converter` 同时接受数组与 `{X,Y,Z}` 对象；写出统一用数组。
- 体积直接降 ~3/4。

**③ 文件头加 `SchemaVersion`，加载时严格校验**
```jsonc
{ "SchemaVersion": 2, "Actions": [...], "Meta": {...} }
```
- 缺字段按 1 处理（旧文件）。
- `SchemaVersion > 当前支持` → 明确报错并拒绝执行，而不是"像今天这样悄悄丢字段"。
- 写在 `PathFile`（`Classes.cs:95`），与 `Meta.LastUpdatedVersion`（路径内容版本）区分开。

**④ 参数做加载期校验（不改变存储类型）**
- 保留 `Arguments: List<string>`（改类型会破坏所有动作实现与 315 份文件），但在**加载时**按 `ActionsManager.actionsList` 的参数个数/类型做一次校验：
  - 参数个数不足 → Warning（`BuildTab` 里标黄）
  - 明显可解析的数值/布尔解析失败 → **Error + 拒绝执行该步**（这正是"少一个参数导致静默 no-op"的根因）
- 后续可选：给 `actionsList` 增加参数类型声明，做真正的强类型化。

**实施注意：`JsonSerializerSettings` 的波及面比看上去大**
它是 `get`-only 单例（`ConfigurationMain.cs:826`），实际被三类用法共用：

| 用途 | 位置 | 是否该换新格式 |
|---|---|---|
| 路径文件读写 | `ContentPathsManager.cs:162/177`、`BuildTab.cs:226` | **是** |
| 配置 / Playlist 深拷贝 | `ConfigurationMain.cs:85-86/411`、`Config.cs:1235`、`MainTab.cs:608` | 否（`JSONClone`，类型静态已知） |
| 多开路径广播 | `MultiboxUtility.cs:464/596`（`PATH_STEPS`） | 否——**这是跨客户端线格式** |

因此**不要直接改这个全局实例**，拆成：
- `JsonSettings.Read`（兼容：`TypeNameHandling.Auto` + 自定义 converter 兜底）
- `JsonSettings.Write`（新：`TypeNameHandling.None` + 判别字段 + 数组坐标）
- 保留 `JsonSerializerSettings` 作为 **Read** 的别名（这样 `JSONClone` 与多开同步行为完全不变）

路径读写两处显式改用 `Write` / `Read`；`JSONClone` 与 `MultiboxUtility` 保持原引用。**`ObjectCreationHandling.Replace` 必须保留**，否则 `JSONClone` 深拷贝语义会退化成覆盖式反序列化。

多开线格式暂不升级，避免新旧版本客户端互相解不出路径；若将来升级，需在 `PATH_STEPS` 消息里加版本前缀并支持双读。

### 10.3 分享改成字符串（不需要文件/URL）

**编码**：紧凑 JSON（短键、省略默认值、数组坐标、判别字段）→ Deflate → Base64Url → 带前缀与校验。

```
ADP1.<base64url>.<crc32-hex>
```
- `ADP1` = AutoDuty Path v1，便于将来演进；`crc32` 用于粘贴截断时立即报错，而不是解析出半条路径。
- 实测口径：Ihuykatumu 那份 10,616 字节/约 50 步的文件，紧凑化后约 1.5~2.5KB，Deflate 到约 700~1100 字节，Base64 后约 **950~1500 字符**（40~60 步路径大致 700~1100 字符）。

**新增 `AutoDuty/Helpers/PathCodec.cs`**
```csharp
internal static class PathCodec
{
    internal const string Prefix = "ADP1.";
    internal static string            Encode(PathFile file);              // → 分享字符串
    internal static PathFile?         Decode(string str, out string error); // 校验前缀/CRC，容错解析
    internal static string[]          Split(string encoded, int chunkSize = 450); // 供游戏内聊天分段
    internal static bool              TryAssemble(IEnumerable<string> chunks, out string encoded, out string error);
}
```
Encode/Decode 内部复用 10.2 的 Read/Write 设置，**不与磁盘格式分叉**（磁盘写的就是紧凑 JSON 的美化版）。

**交互**
| 场景 | 入口 |
|---|---|
| 复制到剪贴板 | `/ad path copy`（整个路径）/ `/ad path copy 12-30`（某段步骤）；BuildTab 加「复制路径 / 复制选中步骤」按钮，显示字符数 |
| 游戏内聊天分段 | `/ad path copy-chat` → 输出若干段 `ADP1C1/4 …`，逐条粘贴即可；导入时按序收齐自动拼装 |
| 粘贴导入 | `/ad path import`（读剪贴板）/ `/ad path import <字符串>` |
| 分段导入 | 连续 `/ad path import <片段>`，`PathCodec.TryAssemble` 判定收齐后提示确认 |
| 落盘 | 导入确认时写 `{pathsDirectory}\({territory}) {name}.json`，`FileSystemWatcher`（`Updater/FileHelper.cs`）自动索引 |

**安全审查（必须做）**
导入的路径本质上是**可执行数据**：`ChatCommand` 能发送任意聊天指令，`Action` / `BLULoad` / `DutySpecificCode` 能触发游戏行为。因此：
- 导入前弹一个只读预览窗：`来源（Author/SourceUrl）` + `步骤数` + **高亮危险动作**（`ChatCommand` / `Action` / `DutySpecificCode` / `BLULoad` / `ModifyIndex`）+ 一键「逐条查看」
- 默认勾选「标记为不覆盖」，写入 `ConfigurationMain.DoNotUpdatePathFiles`（`ConfigurationMain.cs:122`），防止被 `Patcher` 覆盖
- `PathCodec.Decode` 只做数据解析，**不执行任何动作**；解析失败一律拒绝，不做"尽力而为"

**仍需保留的老路（各自有用途）**
1. 打开 `paths` 文件夹手动拖入 .json —— 零代码，适合整包导入
2. URL 导入，复用 `GitHubHelper.DownloadFileAsync(url, localPath)`（`GitHubHelper.cs:27`），适合分享多份路径的仓库
3. 两者都走同一个「审查预览」确认流程

**明确不做**：自建远程仓库 / 短链服务。`Patcher.cs:57` 与 `md5s.json` 的地址目前硬编码为 erdelf 仓库，参数化 base URL 是独立议题——若将来要做，`GitHubHelper.GetPathUpdateInfoAsync` 与 `Patcher.PatchTask` 两处即可。

### 13.3 游戏内手动测试矩阵
1. **卡墙**：在墙边手动 `/ad moveto` 到墙后 → 期望 3 次可见重试 → 暂停 + 声音 + 聊天
2. **漏步骤**：临时从 JSON 删掉一个 `Interactable` → 期望后续 `Boss` 步在 `BossSpawnTimeoutMs` 后报 `boss-missing` 并暂停（**而不是静默完成**）
3. **跳步**：运行中点第 30 步 → 立即停旧寻路并重新寻路；多开下 client 同步
4. **热改**：运行中在当前步之前插入一步 → 当前步仍是同一条（引用跟随）；删除当前步 → 前进到下一步
5. **录制**：跑一遍 Sastasha（solo/unsynced），保存后直接执行，能打完
6. **练级排除**：排除某副本 → 连续多轮都不再排队；自动排除达到阈值后从列表消失，点"清除自动排除"恢复
7. **首次 rebuild**：首次进某副本看到进度条并等待完成；退出重进同一副本不再 rebuild；重启插件后重新 rebuild 一次
8. **回归**：Playlist 模式、Trust 练级、Variant 多路径、Multibox 同步各跑一轮
